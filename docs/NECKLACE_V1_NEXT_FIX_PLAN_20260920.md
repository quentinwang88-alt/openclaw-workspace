# 项链 V1 下一轮修复开发方案

日期：2026-09-20。状态：待开发；本轮仅输出方案，不修改业务代码、不生成脚本或视频。

依据：`docs/NECKLACE_MIXED_V1_REVIEW_20260920.md`。当前实现基线为项链提交 79cb465 / cce51e6 / c5884c2，开发前记录实际 HEAD 与未提交修改，保留用户现有 integration 测试改动。

## 1. 本轮目标与禁止范围

只修四个已复现的问题：公开脚本 ID 门禁绕过、重导后旧审计无法恢复、项链视觉合同丢失冻结配置、数量解析误读否定与未知。补充一条样本的内容调整建议，但不重构内容生成系统。

保持项链开关默认关闭；不改其他类目的模板、配方轮转、口播规则、模型、缓存版本、恢复状态机和发布排期；不批量重写历史稿；不新建数据库或飞书表。

本轮按三个代码提交加一个验收提交完成。前两个生产交接问题必须一起修，避免修好公开 ID 后全部旧稿又因旧审计被永久拦住。

## 2. 修复包 A：公开身份与最新交付快照形成闭环（F1＋F4）

### A1. 先解析可信身份，再决定是否校验

文件：同步器 `core/necklace_handoff.py`、`core/original_batch_source.py`。

现状：导出字段使用 complete_script_id，门禁首先查询内部 script_id；只有提示词像项链时才查公开 ID。真实标题为 HOOK/PROOF/PROOF/ENDING，不触发兜底。

新处理顺序：

```text
读取行的脚本 ID 与现有可信来源定位字段
→ 查询内部 script_id
→ 未命中时查询 complete_script_id（无条件，不依赖提示词）
→ 找到唯一冻结记录后判定 feature_profile
→ 非项链 V1：原同步行为
→ 项链 V1：校验当前实际提示词与最新交付快照
```

具体要求：

- 公开 ID 与内部 ID 的查询不以正文、镜头标题、时长为前提。
- 有 batch_item_id 等可信定位字段时可用于进一步定位；不能信任一段文本里出现的模板名来授予通过。
- 返回明确的 FOUND / NOT_FOUND / SOURCE_UNAVAILABLE / AMBIGUOUS，不再用同一个 None 混淆全部情况。
- 有多个不同条目命中且不能确定唯一来源时报告冲突，不凭“更新时间最新”静默选一个。
- 查询失败不允许降级成“已确认不是项链”。对已声明项链、或有可信项链 V1 来源线索的行，返回 UNVERIFIED 并保留源勾选，不创建目标任务。已解析为旧项链或其他类目的行保持原行为。
- 非项链且没有项链线索的旧行维持现有行为；这不构成对所有无法识别行的全局门禁修复。明确保留该边界，不能声称缺失全部身份信息时仍可准确识别。
- 产品类型字段只能作为“读不到身份时应暂缓”的线索，不能作为通过依据，也不能把所有历史 necklace 自动视为 V1。
- 删除镜头模块签名作为身份查询条件；可保留为诊断提示，不能参与放行权威。
- 全部数据库访问只读，不在同步器 import 生成器顶层 core，避免两个技能包名称冲突。

避免每条公开 ID 都扫描全库：在一次同步调用内批量建立所需 ID 映射，或利用当前 SQLite 支持的 JSON 提取查询。无需本轮新增数据库列／索引。缓存限定本次调用，不跨同步轮次永久缓存旧审计或未命中；不能只看主数据库文件 mtime 判断 WAL 更新。

### A2. 保存“这次实际交付的文本与审计”

文件：生成器 `core/production_script_feishu.py`，必要时在 `core/original_batch_storage.py` 增加窄范围的结果字段合并更新方法；同步器读取端同步适配。

建议在已有 result_json 增加 `delivery_snapshot`，不新建表。它是最新交付快照，原生成结果和旧 render_validation 保留供追溯。新字段必须有真实消费者。

示意字段：

```json
{
  "delivery_snapshot": {
    "schema_version": "necklace-delivery-snapshot-v1",
    "batch_item_id": "...",
    "internal_script_id": "...",
    "complete_script_id": "...",
    "feature_profile": "NECKLACE_MIXED_V1",
    "frozen_contract_hash": "...",
    "source_content_hash": "...",
    "prompt_text": "实际导出的完整提示词",
    "render_validation": {},
    "created_at": "..."
  }
}
```

render_validation 保留现有共享／项链两层 hash、状态与版本。两层当前 hash 算法不同，各自重算，不互相比对。source_content_hash 覆盖本次渲染使用的正文／brief 和冻结依据，排除快照本身及时间戳。

导出顺序：

1. 从同一条冻结源生成一次 checked projection，不重复独立渲染正文与审计。
2. 将完整文本、审计与来源版本组成快照。
3. 项链条目原子合并写入现有 result_json，使用读时版本或内容 hash 做乐观并发检查；不覆盖 checkpoint、其他任务结果和条目状态。
4. 持久化成功后，从该快照构建飞书字段，确保表内正文逐字对应快照。
5. 快照写入失败时不更新该项链行，不取消勾选，明确报错。

如果数据库已保存、飞书更新失败，旧表文本与新快照 hash 不符时应被拒绝；重导幂等更新原记录，不创建第二条脚本，也不触发模型生成。不要宣称 SQLite 与飞书能共享一个事务。

同步器对已识别项链 V1 优先读取 delivery_snapshot；没有快照则要求确定性重导，不能自行制造 PASS。核验快照对应同条目、同脚本、同冻结来源，且当前表内文本 hash、共有／局部审计版本一致。

旧 v1 FAIL → 当前 v2 PASS 的恢复路径是：重新渲染 → 保存最新快照 → 原位更新表 → 同步读新快照后通过。旧失败审计仍留档，但不继续作为当前交付的唯一权威。

对于原来被系统置为“执行校验未通过”的行，重导 PASS 可清除属于本校验器的旧失败说明；不得覆盖人工备注、同步任务 ID 或已完成状态，不自动重新勾选进入生产。普通已经勾选的合格行保持原选择。

### A3. 必须通过的端到端用例

使用实际样本 `SCRIPT_8BCEF97D70205D7F6540` / `SCSCRIPT_40284D07CBCADD28F3F2` 的脱敏隔离 fixture，走真实导出函数与真实同步适配器，mock 外部写入。

| 输入／过程 | 期望 |
| --- | --- |
| 公开 ID＋真实 HOOK/PROOF/PROOF/ENDING 标题＋最新通过文本 | 1 个目标任务 |
| 相同公开 ID＋改成正脸、耳环提示词 | 0 个目标任务，hash／执行错误明确 |
| 删除或改写全部镜头标题 | 仍解析到原项链身份，不得跳过校验 |
| 内部 ID 与公开 ID 分别查询同稿 | 同一冻结身份、同一快照、同一裁决 |
| 旧 v1 FAIL → 当前重导 v2 PASS → 同步 | 正常恢复，不再要求无限重导 |
| 快照保存失败 | 不写飞书、不生成目标任务 |

| 同步第一轮缓存旧审计，第二轮已重导 | 第二轮读取新快照，不命中永久旧缓存 |
| 已知项链来源不存在／库不可读／多条冲突 | 该行拒绝，保留源选择与原因 |
| 耳饰 A/B/C 和已识别旧项链 | 原同步行为与字段不变 |

## 3. 修复包 B：视觉合同完整消费冻结项链快照（F2）

文件：生成器 `core/visual_execution_contract.py::_mixed_visual_contract`。

只在 frozen.feature_profile=NECKLACE_MIXED_V1 时增加窄分支：

- lighting_recipe 从 frozen.environment_recipe 等已冻结字段映射，不再调用无上下文的全局 get_environment_recipe。
- NECK framing 从冻结逐镜 allowed_framing / forbidden_framing 等提取，只汇总佩戴镜；手持／静物继续使用自己的边界，不能把颈部要求提升到所有镜头。
- 保留冻结 label、version、environment、goal 及相关光向、商品原色约束；不得补回当前最新配置假装历史任务原本有这些内容。
- 如果冻结数据缺关键项，报告具体缺口，不返回空结构又标记为完整。历史不完整项链需明确重规划或补足来源，不从共享池随便兜底。
- 非项链条件直接使用原实现，不调整原配方选择、authenticity 或软诊断策略。

测试：使用真实 item1_package 的冻结快照构建 seed；比较冻结配方与 visual_execution_contract 对应字段；捕获模型实际 payload 确认不为空。再临时修改当前项链配置、关闭开关，历史冻结投影仍保持一致。旧四类配饰输出对照不变。

这一步验证的是文字合同投影，不能以通过单测宣称成片没有色偏或穿模。

## 4. 修复包 C：数量按证据判断，不按关键词命中判断（F3）

文件：生成器 `core/necklace_mixed_profile.py` 的 _count_from_anchor_text、resolve_necklace_structure_counts 及 eligibility 相关局部函数。

不修改共享材质／功效分类词表，不在本轮重写所有类目的证据系统。

建议每个数量形成以下局部证据：

```text
value: 明确正整数或 null
status: VERIFIED / UNKNOWN / CONFLICT
source_ref: 结构化字段路径或硬锚点位置
source_text: 支持该数量的原句
polarity: AFFIRMED / NEGATED / UNCERTAIN
```

具体规则：

1. 只读已批准硬锚点和有来源的结构化字段，不读标题或展示建议。
2. 结构化数字须严格为正整数；拒绝 bool、小数截断、零与负数，不能用 int(1.8) 得到 1。
3. 文本按局部断言解析。明确单层、单吊坠为正向证据；“不是双层”不产生 layer_count=2；“不能确认单吊坠”不产生 pendant_count=1。
4. 先判断与目标数量有关的否定／不确定，再提取肯定值；不能把整段存在一个“不是”就全部否定。
5. “不是双层，是单层”可解析为单层；“并非单层，而是双层”解析为双层并拒绝 V1。
6. 结构化字段与肯定硬锚点冲突时保留 CONFLICT，不靠优先级静默覆盖。纯未知文本是否指向同一字段、同一版本无法确定时返回 UNKNOWN/CONFLICT。
7. “有吊坠”只证明存在，不证明数量是1；同理单条可见链段不自动证明完整商品单层。
8. 旧 counts 整数表示可在读取边界兼容，但新规划必须记录来源；不要给缺来源数字制造 STRUCTURE_COUNTS 的伪证据。

最小回归表：

| 输入 | 层数／吊坠数结论 | V1 |
| --- | --- | --- |
| 单层链条，只有一个吊坠 | 1 / 1 | 其他条件满足则通过 |
| 单层链条带吊坠，不能认定单吊坠 | 1 / UNKNOWN | 拒绝并说明缺口 |
| 不是双层，是单层链条，只有一个吊坠 | 1 / 1 | 通过 |
| 并非单层，是双层链，只有一个吊坠 | 2 / 1 | 不适用 |
| 有链条和吊坠，数量看不清 | UNKNOWN / UNKNOWN | 拒绝 |
| 字段为1、另一可靠锚点明确双层 | CONFLICT / 按证据 | 拒绝 |
| 商品盘成两圈，但未确认层数 | UNKNOWN | 拒绝，不猜双层 |
| 数量 true、1.8、0、负数 | 非法／未知 | 拒绝，不转为1 |

本包不要求额外模型调用；无法可靠解析时保留 UNKNOWN，后续由真实商品资料补足。

## 5. 内容优化只落到项链样本，暂不扩大共用规则

现有真实模型样本四镜结构成立，但与参考视频仍有距离。准备下一条候选时明确：

- CU_01：稳定锁骨近景，吊坠落点与链条弧度清楚。
- CU_02：同一位置略宽取景，仅轻微肩部变化；删除收物品、转向出口等生活剧情。
- CU_03：明确掌心作为背景、吊坠正面可辨、链条自然铺落；不是泛泛“少量手指承托商品”。
- CU_04：托盘静置收尾，保留真实接触阴影。
- 口播只说一个主价值，再接一个具体观察；不重复三遍“看得出是H”。语言由现有口播流程生成，不硬编码越南语句子。

先修 B 的输入投影再看真实生成结果，不能直接通过共享提示词增加大量约束来补偿局部配置丢失。确需调整只动 necklace 配置／局部 guidance，不改耳环或全类目 UGC 规则。

## 6. 下一次验收的证据要求

阶段1：三个修复包离线通过，使用真实形态 fixture 重现并消除 F1–F4。保持新开关关闭，不调用模型。

阶段2：选一款真实资料完整的单层单吊坠项链，具备当前商品图、可追溯数量及有效卖点。现有 H 项链 fixture 的人工数量和 TESTSET 卖点只能作为测试，不能复制进生产冒充运营确认。如果资料仍不足，明确报告输入缺口，不降低资格标准。

阶段3：通过现有任务入口对指定商品生成一条新脚本，检查四镜、口播、完整冻结配方、最终审计；再验证公开 ID 导出→同步全链路。记录哪些是离线 mock、真实模型调用、真实外部写入，不能混为一类。

阶段4：按现有进入生产选择生成一条成片，人工看链条连续性、吊坠结构和比例、掌心接触、肤色／商品色、镜间光影，以及实际语音容量。没有成片时只宣布脚本验收通过。

建议提交顺序：A（身份＋快照＋恢复）→ B（冻结投影）→ C（数量证据）→ 验收文档与小批结果。三个代码包都包含各自失败反例与旧行为回归。

最终交付：改动文件清单、F1–F4前后复现结果、旧类目对照、公开 ID 端到端测试、错误恢复测试、实际版本和开关状态，以及真实样本与未覆盖项。不要将“所有单测通过”写成“商品视频效果已经达到参考”。

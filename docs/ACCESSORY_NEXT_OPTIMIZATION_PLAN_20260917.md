**2. 开发包 A：修复最终渲染，先完成离线验收**

主要入口：`core/production_script_renderer.py`、`core/category_execution/accessory.py`、`core/simplified_complete_script.py`、`core/video_prompt_compaction.py`。

目前 renderer 在约 577–584 行按旧 unit_role 覆盖动作。不能只删除某个词；应让新混合模式从同一份每镜执行对象派生动作、构图、商品状态和角色说明。

建议实现一个纯函数构建每镜执行对象，复用已有 capture_unit 与 storyboard 字段，内部名称由实现确定：

| 内容 | 权威来源 | 处理方式 |
| --- | --- | --- |
| 时间、模块、载体、不露脸范围、允许部位、物理状态 | 冻结混合合同 | 硬边界；不能被旧角色弧覆盖 |
| 本镜观察内容、实际动作、运镜 | 已通过审查的成稿 | 在合同内保留具体创意，不替换成类目通用话术 |
| 商品身份、数量与已知结构 | 冻结商品事实 | 全片一致；未知部件不补造 |
| 光线和环境 | 单片冻结配方 | 镜头可以改变角度，不能换另一套配方 |
| 旧 unit_role | 历史兼容／叙事标签 | 可保留作审计，不得再授权身体动作 |

模块边界：HANDHELD_PRODUCT 只允许手与商品；STATIC_PRODUCT 只允许静置商品与环境，允许已规划的小幅运镜；WORN_DETAIL/WORN_RELATION 使用该类目的局部佩戴范围。戒指和腕饰佩戴可能本来就出现手，不能把“手”一律当成手持模块。

同时排查 core_action、movement_guidance、人物反应、视线、手机构图、商品执行关系、末镜 ending_guidance 的投影。连续状态只约束同镜；跨镜 DIRECT_CUT 可以从已拿稳切到已静置、已佩戴，不要求拍摄摘下／戴上过程。

新增最终执行一致性检查，放在拼接和压缩后，而非只检查冻结合同：

- 比较每镜时间、载体、动作、身体范围、商品状态与锚点；结构化校验为主，文本检查兜底。
- 分清正向动作和“不得出现头部”这样的禁止说明，不能用命中“头部”关键词即判错。
- 报告包含 shot_id、冲突字段、来源及实际值，明确是生成、渲染还是压缩引入。
- 使用最终 prompt_hash + renderer_version 绑定结果；生产交接如果重渲染，必须重新检查或验证 hash 相同。
- 保留稿件供审阅；确定的执行冲突不得进入视频提交。复用已有交接检查点，不新建审批表，不让用户重复确认已经做出的进入生产决定。
- 技术层可以保留“脚本文本已完成”的状态，但可生产数量必须单独扣除执行冲突。不要把可离线修复的渲染失败直接转成会重新调用模型的 SCRIPT_FAILED。

最小审计字段建议写入现有结果 JSON：render_validation.status、issues、prompt_hash、renderer_version。新增字段必须在最终交接处有实际消费者。

验收：重渲染现有四条稿，8 个非佩戴镜零旧人物动作污染，16 镜均满足各自边界；时间轴、直接切镜、已确认结构、不露脸不回退；压缩后结果同样通过。此包不需要调用生成模型。

**3. 开发包 B：同时修复视觉差异、主题差异与恢复幂等**

主要入口：`core/accessory_mixed_templates.py` 中 mixed_signature_from_script、mixed_semantic_signature、compare_mixed_signatures、_new_observation_jobs；`core/original_batch_allocator.py`；`core/original_batch_executor.py` 中历史读取、签名写入和交付统计；`core/storage.py`。

B1：实际成稿特征与计划要求分离。

保留原始全文 hash 用于精确相同检测，但不再把“hash 不同”解释成镜头或语义不同。为实际成稿建立有版本的特征，以下为建议字段，不表示当前已存在：

- 每镜：actual_module、visible_subject、observed_part_or_relation、action_or_state、framing_scale、sequence_position、source_refs。
- 主题：audience_question、core_value、visible_answer、claim_type、source_refs。
- 表层：背景、光影、音乐、修饰表达。

source_refs 指向该稿 storyboard／动作／口播的具体字段或原句；主题必须来自实际成稿，不能从 template_id、theme_id、argument ID 或冻结 observation_job 直接认领。成稿与计划不一致时报告差异，不用计划值修饰成稿评分。

提取优先复用现有成稿审查和结构化产物；规则无法可靠识别语义时，最多进行一次有缓存的整稿特征提取，不为每一对历史稿分别调用模型，不增加常驻服务。无法落回原文的特征不用于宣布差异通过。缓存以成稿内容 hash 和提取版本为键。

比较时必须区分“灰色背景”与“灰色商品”：前者属于风格，后者可能是商品变款错误。结构、装饰数量和商品原色不能被当作无关词删除。

B2：明确裁决和统计口径。

| 实际情况 | 裁决 | 独立主题数 | 有效执行变体数 |
| --- | --- | --- | --- |
| 正文与实际展示相同 | EXACT_DUPLICATE | 不增加 | 不增加 |
| 仅背景、光线、近义措辞改变 | SURFACE_ONLY | 不增加 | 不增加 |
| 仅将同组镜头换序，未增加观察或叙事信息 | 可保留 EXECUTION_VARIANT，标记 order_only | 不增加 | 默认不增加；不自动当成实质差异 |
| 同主题，但新增明确且受支持的观察内容／关系 | EXECUTION_VARIANT | 不增加 | 增加 |
| 不同购买理由，且成稿有相应画面或可靠信息支撑 | DISTINCT_THEME | 增加 | 不重复计为变体 |
| 证据不充分、旧版不可比、提取不确定 | NEEDS_REVIEW | 待复核 | 待复核 |

只有实际序列比较证实顺序变化时才输出 SHOT_ORDER_DIFFERS。新增观察内容不要求是功能测试，造型、比例、装饰层次、搭配关系都可以成立。只有口播换卖点、四镜完全相同，不自动计为独立视频。

报告分别展示：请求数、生成成功数、执行校验通过数、独立主题数、有效变体数、重复／表层变化数、待复核数、可生产数。主题＋变体合计时按唯一 script_id 去重。

NEEDS_REVIEW 保留原稿与已有人工选择流程，不自动判失败、不无限重写；未复核前不计入已确认独立数量。明确重复继续使用 SCRIPT_DUPLICATE。确定的最终渲染冲突由开发包 A 的执行检查处理，不与“相似性不确定”混用。

B3：商品证据与主题语义分开。

当前 semantic digest 对 claim/evidence ID 求 hash，不能代表主题。商品事实签名只回答“用了哪些商品事实”；内容签名比较观众问题、购买理由与实际表达，保留来源引用但不依赖 ID 是否不同。

规划时把 thesis 的 ARGUMENT_OPERATOR_* 回退改成所选卖点的可读命题，保留原 ID 在来源字段。缺少具体主线时标明输入缺口，不能用内部 ID 冒充主题文案。

B4：排除自己并保证恢复可重入。

- 历史引用排除当前 creative_usage_id 和 batch_item_id；有 script_id 时增加交叉保护。
- 同批兄弟与历史的同一条记录只比较一次，不能为排除自己而排除整个当前批次。
- 签名写回按稳定条目键幂等更新；失败阶段可恢复，不重复累计台账或独立数量。
- 补“写入成稿签名后、READY 落盘前中断”的测试；优先利用已有生成检查点恢复，避免仅为台账失败再次付费生成。
- 历史写入失败时保留稿件并报告 history_persisted=false，后续补写；不能报告已完成跨批去重保护。
- 同商品范围保留；历史版本不同须转换或明确不可比，不能默认 DISTINCT。可从现有正文离线重建，不修改历史原稿。

首期仅对本功能已有串行执行路径承诺一致性。若实际存在同 SKU 并发生成，需复用现有锁／事务做最终复核与登记串行化，不能两个进程都在空历史下同时通过。

**4. 开发包 C：把商品、主题、分镜与口播统一**

主要入口：`core/product_type_resolution.py`、`core/product_selling_argument_adapter.py`、`core/semantic_spine.py`、`core/category_execution/accessory.py`、`core/simplified_complete_script.py`，以及当前 15 秒实际使用的中央口播桥接。沿用当前调用链，不误改 longform 专属口播路径。

C1：事实适配。

每个所选卖点保留原文、来源、商品图片版本、事实类型、适配结论。未知部件仅排除依赖该部件的主题；明确冲突需解决，不让生成模型自行选择一方。人工运营输入提供意图，不自动构成真实体验记录。

- 外观与装饰事实：原图或可靠规格支持。
- 审美感受：“我喜欢这种层次”“看起来柔和”可以自然表达。
- 搭配建议：与实际冻结发型／穿搭兼容，不假装已经展示多个场景。
- 性能、材质、佩戴体验：需要相应来源；外观看起来轻盈不等于重量轻或久戴舒适。
- “我试了一天”“随手一夹就完成”：需要真实体验／过程依据，不由生成画面反向证明商品性能。

复用女装纠错原则：身份纠错绑定 SKU 与图片版本，负向和未知不进入正向结构事实。商品图定义商品，人物参考定义身份，首帧只定义构图。

C2：每条一条明确主线，模板负责组织展示。

复用 semantic_spine，冻结观众问题、核心价值、事实依据、可见回答、表达边界。主线同时进入观察任务和中央口播，避免生成两个互不相干的主题。

| 模块 | 本轮应落实的任务 |
| --- | --- |
| 佩戴开场或造型开场 | 直接展示与本条主线有关的结果／完整形状 |
| 手持 | 看清商品本体轮廓、排列或已确认结构 |
| 静物 | 集中看一个需要稳定画面才能看清的细节，避免再罗列全部特征 |
| 佩戴关系 | 解释商品与发型、耳垂、手部、袖口等的比例／搭配关系 |

每镜任务与主线相关即可，不要求每镜都有功效证明。首尾可以同一佩戴状态，但应提供细节与整体关系的区别；不把重复裁切自动算作第二个观察。

C3：口播写作做减法。

中央口播只接收目标语言、一个主价值、必要事实、实际可见回答、可选语境及体验边界，不投喂全部候选卖点、动作库和工程错误码。不逐镜报幕，不强制填满 15 秒，不默认所有开头都写“我刚发现”。

成稿核对区分三类：可见结果要落在具体镜头；规格事实核对来源但不强求每句镜头证明；建议与审美不伪装为实测。口播存在明确事实错误时使用现有一次定向修订；仅口播错误不重做视觉，商品身份变动才重做受影响规划。超过修订上限保留结果待审，不循环付费。

语言校验、母语自然度、实际音频时长分开报告。交付文档语言标签动态读取 target_language，修复越南语被标“马来语”的导出错误。

**6. 色调与账号风格：复用配置，约束实际选择**

冻结单片环境完整快照：主光方向、柔硬程度、白平衡倾向、台面、背景、曝光与高光边界。四镜可换角度，商品原色不随暖背景变化。首帧与视频提示词读取同一快照。

账号配置负责筛选允许的配方、主题、口吻和场景范围。先筛允许集合，再按近期使用情况轮换；禁止先全局轮转配方再补账号标签。主题不兼容时从同商品其他有效主线中选，不能改造商品事实迎合账号。

原女装“一衣多穿”不直接用于配饰。确需“一饰多搭”，必须有两个已计划、兼容的搭配结果；当前单套穿搭四镜稿只能说一个搭配或建议，不能包装成已经演示多搭。

两个账号的最终配饰主题配额与配方名单采用用户已配置值；当前 review 没有验证两个账号的发布样本，不能宣称已完成账号一致性验收。配置缺失时报告缺口，不替用户悄悄修改定位。本包不新建账号管理系统。

提示词优先删除重复的角色说明、重复禁令和冗余环境描述，目标落回现有内部预算。身份锚点、每镜载体和动作边界不可截断。超内部 4000 字与远端硬限额分开报告，不因 over_limit=true 自动判生成失败。

**7. 验收矩阵与实施顺序**

| 阶段 | 样本／方法 | 放行条件 |
| --- | --- | --- |
| A 离线执行修复 | 当前四稿全量重渲染；检查压缩前后 | 16 镜边界一致，8 个非佩戴镜零旧动作污染；硬冲突确实被生产交接拦住 |
| B 离线差异与恢复 | 精确重复、换背景、近义改写、真实换序、新观察、同事实不同主题、同主题不同 ID、跨 SKU、自身恢复、历史版本不兼容 | 每类裁决符合表格；无自我拒绝；签名和数量幂等；计划值不能冒充成稿特征 |
| C 内容回归 | 四条现有稿逐项审阅＋针对花朵 B 的事实／口播用例 | 明确购买理由；手持静物不机械重复；无无源体验升级；口播所称眼前结果实际存在 |
| D 小批真实脚本 | 两款现有发饰各生成 1 条；耳饰、腕饰、戒指各 1 条；另选 1 个商品在后续批次生成 1 条，共 6 条候选 | 总体覆盖 A/B/C；复核真实主题和执行差异、跨批引用；不足不凑数 |
| E 成片与账号 | 从通过稿中选两个发饰候选及一个其他配饰候选；按对应账号配置生成后审阅 | 商品结构／数量／颜色一致；无露脸与部位冲突；自然接触和真实光影；口播容量合适；账号主题与配方兼容 |

阶段 D/E 是后续运行验收计划，本次仅输出方案，不执行模型调用。选款缺乏某结构证据时保留 UNKNOWN，不为覆盖测试用例虚构事实。

建议按 A → B → C → D → E 实施；账号配置选择与导出标签可随 C 完成。A/B 先用旧稿和纯函数回归，避免每修一处就重新跑整批模型。

10–20 条只作为候选目标。最终报告可以是“3 个独立主题、4 个有效变体、其余近似／不支持”，不能把背景数量、模板排列数量或生成成功数直接当成原创质量指标，也不据内部裁决承诺平台一定判定为原创。

**8. 开发交付要求**

交付代码、定向测试、版本与兼容说明、四稿渲染前后对照、差异裁决样例、恢复故障注入结果，以及实际跑批报告。报告必须分清离线复现、模型真实生成、实际成片三种证据。

字段与签名版本采用增量方式，旧签名仍可审计；不能静默把旧 hash 当新版语义签名。新规则作用于新混合任务；对指定历史稿重渲染只产生带版本的审阅产物，不覆盖旧正式交付。

部署时同步已验收开发源至安装镜像，验证官方入口实际加载版本，并保留可回退版本。当前仓库已有本轮未提交修改，开发模型需在现有改动上继续，不重置或覆盖用户工作。

任务完成标准是“正确合同能到达最终执行、差异裁决可信、内容与商品一致、代表样本通过”，不是“测试全绿”或“生成数量达标”。

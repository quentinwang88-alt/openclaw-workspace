## 1. 背景与已确定决策

泰国旅行穿搭原生图文已获得用户初步认可的业务反馈，经历过主题脱节、重复素材、人物 AI 感、歪头、造型相似、质检反复重生、标题排版及发布接线等多轮优化。现在拓展到 MX 假发，目标是借用已经成熟的任务、资产、原生图文排版和 CreatOK 发布基础，尽快生产可看的西语假发内容。

用户明确要求：**不要因 MX 开发改动影响泰国线**。本轮不能顺带重构泰国旅行、修其历史数据、替换其模型或改其质检规则。当前工作区存在大量未提交和并行开发改动，不能整体覆盖文件或回滚工作区。

已确定：
- 首个内容主题：周末换个发型，你选哪款？对应现有 MX_PICK_YOUR_HAIR 内容逻辑。
- 输出：4 张独立竖图，A 本身承担首图；随后 B、C、D，D 放简短 CTA。不增加重复封面或四宫格页。
- 人物：用户已选 A（日常亲和），不再要求重新三选一。
- 首轮：NO_PRODUCT，无商品挂车；使用假发灵感，不虚构指定商品变体。
- 一篇内同一人物，发型明确可变。服装、妆容和摄影氛围大体稳定。
- 继续使用现有图文任务表、执行/确认发布状态及原生图文 CreatOK 链路，不拼成视频。
- 不开发账号评分、Benchmark、新后台或全市场内容中台。

## 4. 保护泰国线：必须遵守的开发边界

- Feishu 原生图文执行入口：仅匹配新 MX 任务/冻结批次时进入 MX preparation/retake，否则原实现。

## 5. 第一版内容合同

预设显示名称仍为“图文｜MX｜四选一发型”。建议新增 Recipe：
`PHOTO_MX_PICK_YOUR_HAIR_V2`，`recipe_key=MX_PICK_YOUR_HAIR`，execution_flow=`mx_wig_choice_v1`。
旧文件名 V1 内部版本已为 2，接手者需核验版本唯一性，避免覆盖已冻结记录。以新ID新增、定向切预设；不要复用相同ID偷偷改变含义。

默认主题：周末换个发型，你选哪款？内部 theme_key=`MX_WEEKEND_HAIR_CHOICE`。
首批选择轴为 `style`，不标为纯长度实验，因为 Bob、直发、波浪同时涉及轮廓与卷度。

| 页 | 源角色 | 计划示例 | 文字职责 |

| 1 | hair_a | 利落短 Bob | 主题短标题 + 小号 A 标识；此页就是首图 |

正文自然描述这组选择，不提价格、促销、生发、真人发等未经提供的产品事实。西语示例是种子，不是每篇必须重复的固定句。

## 6. 参考图与产品编码：最小运营负担

必填仅为生产预设、店铺和数量；主题默认周末发型，A 由账号绑定。用户不上传参考也可以按 Recipe 自动生图，不得要求先制作四套成片。

参考图可选：发型灵感、环境、摄影风格；一张允许多个用途。首版复用现有参考附件和内容要求字段，由 MX 分析器输出用途，运营可在内容要求中覆盖，如“第一张参考发型，第二张只参考环境”。不要因此新增 JSON 列或重做所有参考图下拉。

历史“穿搭参考”在 MX 分支可作为造型灵感处理，但不能要求假发任务提供裤子和鞋子；若无法无歧义映射则显示简短补充提示，不静默读取成 TH 主题。TH 单元格选项含旅行主题时，MX 给出明确不兼容提示，不触发旅行逻辑。

首版不支持产品编码驱动的四选一。MX 新任务一旦填产品编码，在付费生成前提示：“本预设生成四款发型灵感；单款商品模式暂未开放，请清空产品编码或使用后续单品预设。”保留用户输入，不自动清空或忽略。

原因：一款假发不能擅自换长度、颜色后仍都宣称为该商品。后续单品模式需设计真实可行的佩戴/场合展示，与本轮分开。不要为此限制现有 TH 的商品编码使用。

## 7. 最小实现结构

建议新增三个小型模块，命名可按现有风格调整，不建插件注册框架：

1. `services/photo_wig_planner.py`：MX 输入归一、参考职责、四款计划/西语文案、计划冻结、新请求构建与四页生产计划映射。此处“planner”包含创意计划和翻译到既有 revision/package 的适配，不复制底层数据库写入基础设施。
2. `services/photo_wig_supply.py`：根据冻结 option 生成图片，复用现有图片客户端、格式归一、有限并发及文件持久化；维护 MX 独立缓存清单、资格信息和定向重拍。
3. `services/photo_wig_qa.py`：有限的组级头发/人物检查，以及 MX 最终文案与排版检查；复用视觉客户端和图片解码能力。

MX 新布局 `PHOTO_MX_HAIR_CARD_V1.json` 使用既有可执行 layout schema。可借鉴旅行字号/安全区，但建立独立配置，不改原旅行布局。标题避让发顶、脸部与发型主体；无需要求图片模型写西语文字，文字统一由排版器叠加。

复用既有 Task、TaskRevision、AssetSet、ContentPackage、ProductionBatch、原生图文 exporter、发布冻结与 main schedule bridge。默认不新增数据库表或列；使用已有 JSON 快照保存明确版本字段。若发现数据库或装载器限制，先给出具体限制及最小差异，不能顺势做平台迁移。

### 7.1 四页合同接线

MX source_roles 使用 hair_a..hair_d，只有4个真实源资产，不创建 cover_seed，不额外复制 hair_a。源槽位数量和输出页数量在 MX 均为4，显式记录 requested_shot_count=4。

新冻结请求保存 `execution_flow=mx_wig_choice_v1`、MX 内容卡、recipe/layout/persona/asset 快照和 copy。新请求校验器必须同时验证 market/category/recipe/flow/locale及hash，不能仅凭一个布尔标记放行4页。

通用 Planner 入口仅增加 MX 定向调用；MX 映射器按内容卡4页建立 slides 和4源 shots，仍通过现有 repository 创建 revision/package。不能把4条 copy送进旧 validate_copy 默认5条路径。

通用 content card 校验只增加明确 MX 分派，或由 MX 请求校验器独立校验后提交已有保存接口；不得把所有 unknown visual_rules直接忽略。需要验证的发型证据包括 role/source哈希、规划属性、实际QA结论；不能伪造外套/下装属性蒙混资格检查。

在方案实施前画出实际调用链，确保 request factory → validate frozen → task intake → planner → producer → exporter → QA → release 的每一站都能识别4页。特别检查默认参数、caption/slide_texts长度、源槽位、首图index、末页CTA、上传张数。

## 8. 人物与图像质量策略

人物主参考始终为用户选定的 A，同组不拿上一张新生图作为唯一脸部权威源。每个请求显式区分人物、发型、环境图片，实际上传列表与说明必须一一对应，不能上传4张却写“前两张是人物、后两张是商品”。

构图以胸像/半身为主，长发扩大取景看清发尾。不要求完整鞋子、统一头身比或固定4机位。衣服简单且与头发有明暗对比。真实皮肤不等于刻意增加毛孔/疲态；精致不等于过度磨皮。不得把脸磨成另一张脸来提高“颜值”。

质检设计：
- 免费技术检查：文件可解码、尺寸与比例、sha、4个角色唯一、文案完整、无重复文件冒充不同款。
- 一次组级视觉检查：明显换脸/畸形、严重头发粘脸、四款实质重复、核心发型严重不符。返回具体受影响 role 和原因。
- 小差异只记录：自然肤色受光差异、个别发丝、轻微微笑和视线变化、非核心卷度细节。
- 发色变化由计划决定，不用全图色温/色差阈值把不同发色拉成一样。刘海可遮部分发际线，不要求所有选项强行露额头。
- 每张最多自动修复1次；修复后可对修复图及必要对照做一次复查。明确硬伤仍存在则标需处理，保留其他合格图；没有结构性问题但仅审美不足则作为质量备注，不假装平台流量评分。
- 最终排版检查沿用现有渲染技术检查；MX薄层检查西语标题/选项一致、字体重音符号、倒问号以及标题不挡头发。不要再叠三套视觉终审。

西语字符纯度检查不能代替语义本地化：目前 locale_quality 主要排除中文/泰文，英语句子也可能通过；在同一次规划或QA中核验自然es-MX，不新增独立多轮文案审核流水线。

## 9. 批量、续跑与重拍

## 10. 发布链路

无挂车发布，复用现有自动配乐字段/渠道策略，禁止转视频或恢复本地BGM。缺CreatOK能力/授权时明确提示，不自动改走NeoBund。不要为此改其他账户的渠道决策。

**一、背景与本轮边界**

上轮已实现主题文案语言参数、无主题重拍恢复、指定围巾检查提示、入口分组、定向播种和 VNPS01 路由。围巾四选一已有真实单篇成片；围巾旅行已有付费源图和新的越南语规划，尚需完成最终成片复验。

复核时 HEAD 为 `1d9b55e`，另有未提交的 locale/profile 修复及 `tests/test_photo_copy_locale_binding.py`。接手者先核对最新状态，保留其他会话修改，不按旧提交覆盖工作区。审查期间预设曾被临时启用；当时 1,305 项测试的 10 项失败均与目录或停用状态断言有关，不能直接视为算法回归，也不能宣布全绿。

本轮只修三个问题：

1. 素材版本冲突会先覆盖历史行，再被回读检查发现。
2. 围巾核心商品检查失败后，没有角色进入重拍，导致 QA 空转。
3. 新增语言字段使部分旧计划不兼容，连带归档付费素材并重新生成。

不改 TH 成熟选题、Prompt、首图、页序和审美标准；不增加质检轮次、全局评分门槛、人工逐篇审核或新业务表。账号定位分配、更多主题和数据看板继续后置。

**二、修复 A：素材入库必须防止旧记录被覆盖（最高优先级）**

现状链路：

- `PhotoAssetSupplyService.qualify` 只查询同 category/market 下 enabled 素材，计算同 key 最大版本＋1。
- 数据库唯一索引 `uq_opv_asset_set_version` 实际是 `(asset_set_key, asset_set_version)`，与 category、market、status 无关。
- `AssetSetService.save` 调用 `RdsRepository.upsert_asset_set`，后者进入通用 `_upsert`，使用 `ON DUPLICATE KEY UPDATE` 并提交。
- 冲突命中另一个 asset_set_id 时，其内容已被更新；qualify 的后置回读只能发现悬空新 ID，无法撤销旧行损坏。

**A1．把新增素材与旧素材状态更新分开处理**

在素材专用仓储方法中处理，不修改所有业务表共用的 `_upsert` 语义：

- 新素材使用普通 INSERT；唯一键冲突不得覆盖任意已有行。
- 相同 asset_set_id 重试时，核实素材身份一致后返回数据库中的实际记录和版本，实现幂等。
- 需要修改状态时，只按明确的 asset_set_id 更新允许变更的状态字段；不借状态更新重写素材内容、市场和类别。
- 检查 `upsert_asset_set` 的实际调用方，确保所有素材写入口都不会绕回“版本冲突覆盖另一 ID”的路径。可以保留原方法名作为兼容入口，但内部执行素材专用语义。
- `AssetSetService.save` 写入后读不到记录时必须报错，不能再返回一个从未持久化的内存对象。

**A2．版本号与唯一索引口径一致，并处理并发**

- 按 asset_set_key 查询全部状态、全部市场／类别的最大版本；查询范围与唯一索引一致。
- 在素材专用事务中申请版本并尝试 INSERT。
- 相同 ID 并发：读取已存在记录，确认来源图片 hash、key、类别、市场及绑定一致后复用实际版本；不要因为本次拟申请版本不同而误判为内容变化。
- 不同 ID 争用同 key/version：回滚该次写入，重新读取版本并进行有限次数的入库重试。优先沿用项目已有冲突重试约定，没有则局部限制最多三次；禁止无限循环。
- 超出重试次数时保留 stage 和已生成图片，报告“素材登记冲突，可重试登记”。不得触发重新生图。
- 仅“全状态 max＋1”不够，并发仍会撞号；必须同时保证冲突写入不会覆盖旧内容。

保留现有唯一索引，不把 status 加进唯一键，也不通过删除停用历史行来腾版本。无需为此新增一套分布式锁系统。

**A3．现有受影响记录只做定向核查**

复核报告提及 `ASSET_TH_WOMENSWEAR_CHOICE_V1/V2` 曾被 VN 内容覆盖并已停用。

- 先只读核对这两条及本轮关联 VN 素材，保存当前内容和引用关系快照。
- 有可靠旧快照时才定向恢复原记录；缺少证据时保持停用并记录原因，不能用猜测内容恢复或启用。
- 不删除旧 ID，不批量改写历史任务的 pin，不全量重导 TH/MX 配置。
- 若本轮需要登记已生成 VN 图片，复用其字节与清单，走修好的素材插入路径。

主要文件：

- `repositories/rds_repository.py`
- `services/asset_set_service.py`
- `services/photo_asset_supply.py`
- `tests/test_rds_repository.py`
- `tests/test_photo_profile_market_binding.py`／`tests/test_photo_asset_supply.py`

验收必须覆盖：

1. 同 key 的最高版本已 disabled，新增仍使用更高版本，旧行全部字段不变。
2. 同 key 已有其他 category/market 的版本，新插入不覆盖它。
3. 两个不同素材同时争用版本，最终 ID 各自存在，或一方可重试失败；不能任何一方覆盖另一方。
4. 同素材重复登记返回同一实际 ID/version，无重复记录。
5. 登记失败重试不调用图片生成器。

测试应检查数据库约束和事务行为，可使用本地隔离数据库或按真实唯一键模拟的仓储替身；不能只让 fake 抛异常，然后断言“报错了”。正式生产数据库不能作为冲突测试场。

**三、修复 B：核心商品失败必须进入定向重拍**

已复现的输入：

```text
role_findings: look_b passed=false
issues: 围巾颜色家族错误／围巾结构错误／指定围巾完全看不到
missing_major_garment=false
```

当前 `_failed_roles` 返回 `([], True)`：中文关键词白名单将其当作细节提示，但整组 passed 仍为 false。程序不重生任何图片，只增加修复次数，最终 group_failed。

**B1．为已存在的核心商品判断补一个结构化归因信号**

- 优先检查现有逐 Look 返回结构能否承载；如没有合适字段，增加 `core_product_mismatch` 布尔字段即可，不再增加一套细项评分。
- 仅在本篇指定商品时启用，含义限于当前已经约定的明显缺失、明显换款、核心颜色／图案／结构明显错误。
- 图片发送顺序、实际商品参考图和 product_context 沿用上轮修复。
- 从模型响应解析、标准化后的 role_findings 到 `_failed_roles` 全程保留该字段，不能只改 prompt。
- 字段缺失的旧响应保持旧处理路径，不以缺少新增字段为理由追溯拦截全部历史任务；新调用要求明确逐角色结果。

**B2．修复归因与组级判定一致**

- 指定商品且某 Look 的该标志为 true：直接将该 Look 纳入 failed_roles，不经过中文关键词过滤。
- 整组 passed 不得覆盖明确的核心商品硬失败；聚合结果与逐 Look 结果保持一致。
- 非指定商品情况下，普通围巾／配饰变化仍可宽容，不能强制所有自由搭配使用同一条围巾。
- 不简单把所有 passed=false 都升级为硬失败，否则会恢复此前单品细节反复卡 QA 的问题。
- 复用当前角色摘除、生成、重新检查和次数上限。只重拍实际失败 Look。
- 有失败但没有可执行修复角色时，不得把“对原图再查一次”记为完成了一轮修复。沿用已有无归因处理或明确返回无法归因的可读错误，不无限重查。

主要文件：

- `services/photo_reference_vision.py::review_alignment/_alignment_prompt`
- `services/photo_style_reference_supply.py::_failed_roles` 及组级修复循环
- `tests/test_photo_reference_vision.py`
- `tests/test_photo_theme_reference.py` 或已有供给流程测试

验收必须贯穿 QA → 归因 → 实际生成器调用：

1. 第一次 QA 判 B 商品不符，生成器仅收到 B 一次重生，A/C/D 字节不变；第二次检查通过则任务完成。
2. 商品修复仍失败时按现有次数上限结束，不增加新 QA 轮次。
3. 未指定商品时颜色微差、围法、褶皱和普通配饰差异不触发新硬门槛。
4. 上轮三个中文复现描述不再导致空转；判断依据是结构化信号，不靠继续补词表。

**四、修复 C：语言兼容与文案修复不得连带重生源图**

影响范围：没有冻结 batch、已有旧 plan.json 和付费素材、且素材段仍需执行的任务。已冻结 batch 不走该新契约路径，应保持原恢复行为。

现状：新增 `input_contract['publish_locale']` 改变 hash；`PhotoContentPlanStore.load_or_create` 抛输入变化异常；工作流把 content_plan 和该记录全部 style_reference_supply 一起归档。即使实际语言和画面要求未变，也可能重新付费生图。

**C1．给新增字段做窄兼容，不放宽整个指纹检查**

- 在比较完整契约前，识别“旧契约缺 publish_locale”的既定升级情形。
- 只有移除这一新增键后其余契约一致、旧任务绑定能够证明实际语言一致时，才补记该字段并重新保存契约 hash。
- 原语言应来自可靠的历史绑定或冻结元信息；不能只用当前预设默认值推断用户没有改语言。
- 无法确认时保留旧计划和素材，给出可读原因；不要自动归档源图并重新生成。
- 真正修改了商品、人物、参考图、穿搭或场景等视觉输入时，继续保留现有变更检查。
- 不全量批改所有历史 plan.json，也不把所有 hash 不匹配都判为可兼容。

**C2．单独处理“旧文案错语言，但源图可用”**

- 复用已完成的源图，按正确 locale／profile 重建标题、封面文字、标签、CTA、hashtags 和相应冻结结果。
- 保留旧 look 规划、商品身份、人物与场景等视觉部分；只更新明确的文案字段。不可把整个内容计划重新生成后，假定新计划与旧图仍相符。
- 图片生成指纹当前可能包含 variation 中的文案：通过受限兼容处理确认仅文案变化，不能直接全局删除 hash 中的字段或无条件重设基线。
- 排版和文字覆盖可以重做，但图片生成器调用次数必须为零。
- 已有冻结批次／成片时走现有修订机制，保留版本记录；已经进入发布队列或已发布的内容沿用现有不可变与重做检查，不原地篡改发布清单。
- 后续只有真正的视觉变化才进入现有素材归档／重新生成路径。新增的纯契约字段和文案变更不能默认归档全部 style_reference_supply。

主要文件：

- `services/feishu_workflow.py`：input_contract、错误恢复和 `_archive_photo_planning_state` 调用点
- `services/photo_content_planner.py::PhotoContentPlanStore.load_or_create`

- 复用现有 `services/photo_locale.py` 和未提交的 locale/profile 修复，不重建语言模块

验收：

1. 同语言旧计划，仅新增 publish_locale：图片路径和 hash 不变，生成器零调用，能够继续冻结／排版。
2. 旧 VN 泰文文案：保留原四张付费图，最终越南语通过现有文案校验，生成器零调用。
3. 真实改变场景或商品不被上述兼容吞掉。
4. 已冻结批次按原路径恢复，TH 成熟输出不变。
5. 失败期间仍保留可恢复的计划、素材和修订记录。

**五、提交、配置与真实验收顺序**

1. 先确认当前 HEAD、未提交修改和本机正在执行的任务。不覆盖其他会话的语言补丁，也不在另一任务改配置时声称已取得稳定测试基线。
2. 独立完成 A、B、C 的代码与针对性测试，提交中注明采用了哪些已有修改。
3. 明确本轮最终配置：开发默认还是已验证生产配置。对应更新准确的目录／状态断言；保留独立 fixture 检查 disabled 行为，不能把旧停用断言简单删除。
4. 不要为了跑绿在正式机上来回切换生产配置。需要两种配置测试时使用临时配置副本。
5. 完成稳定版本回归后，先复用旅行 A 行的现有四张图片，完成越南语成片。若该行已有冻结批次，先检查修订路径，不删除批次强行回到首跑。
6. 再选择一条围巾四选一三篇任务验证恢复；指定商品的真实验证需要真实同款商品资料，未备齐时不阻塞已验证的自由搭配能力，但不能宣称商品模式已验收。
7. 原生图文发布沿用现有确认发布授权与渠道，不因修复完成自动发布全部测试记录。

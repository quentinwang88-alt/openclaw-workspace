**三、运营体验和最小数据设计**

预期体验：

> 账号表维护一次定位与参考图 → 图文任务选择目标账号 → 系统读取默认定位 → 填商品／地点／本篇要求 → 生成与回写 → 点击现有确认发布 → 内容只进入该账号。

不要求发布时再次选账号，不新增人工审核步骤。

**3.1 账号表是运营配置的唯一来源**

先核实截图是哪张表。优先在现有账号管理表复用截图已有列；若截图是另外一张已有定位表，用明确账号 ID 关联读取，选定其中一处作为主配置，不在两张表各维护一份。

| 信息 | 运营如何维护 | 程序如何使用 |
|---|---|---|
| 真实账号 ID／店铺／市场 | 复用现有字段 | 关联、校验和投递，不用显示名做主键 |
| 定位、题材、核心场景 | 复用已有文本列 | 合并为简短定位说明，注入内容规划 |
| 视频风格 | 复用现有文本列；说明其对图文摄影同样生效 | 形成摄影、配色和构图基准 |
| 风格图片 | 复用附件 | 作为可重复使用的默认参考图，保存附件身份与内容 hash |
| 内容表达 | 若现有定位字段不可稳定映射，最多新增一个单选：搭配灵感／实用指南 | 对应文案与排版表达，不对应两套 Recipe |
| 文案 | 沿用为风格示例／要求，并在字段说明中明确 | 不能把示例“5°C”或“10月东京”每篇原样复制为任务事实 |

不新增 Market、Category、Recipe、Template 等运营必填项。产品参与继续由任务商品编码决定，不新增“老号必须商品”硬限制；重点号允许少量符合定位的自由搭配。

程序内部将上述值规范化为一个小对象 `photo_content_profile`，包括定位说明、表达模式、视觉说明、参考附件指纹和配置指纹。这是同步数据，不让运营写 JSON。人物资产继续沿用已有库；同一人物可用于两个账号，不强制为区分账号再建两套人物。

**3.2 最小持久化**

- 发布器账号配置若无合适扩展字段，可增加一个 nullable 的 `photo_content_profile_json` 缓存列，由同步程序生成。需要对应 SQLite 兼容 migration，旧账号默认为空。
- 同一物理账号的 Neobund／CreatOK 多条连接行共享内容定位：非空配置一致则合并，空行继承；冲突只标记该账号图文定位待修，不随机取第一条，也不暂停其原有视频业务。
- 生成时把 profile 内容／指纹、参考图身份及目标真实账号写入现有请求／批次快照，后续重拍按冻结值恢复。
- 内部生产资料 `ContentTask.account_id=OPV_...` 如有现有外键用途就保留；另用 `target_publish_account_id` 表示真实投递账号，不能直接拿真实 TikTok 用户名替换 OPV 外键。
- 优先用既有 request、plan、release manifest、主队列 `script_text` JSON 承载目标和快照，不为此新增任务关系表。需要新列时说明消费者与必要性。

**四、工作包 A：账号定位从生成到发布完整贯穿**

**A1．任务入口解析**

- 在现有图文任务表增加／复用“目标账号”，从已有账号管理记录选择并解析真实 ID。
- 已填写目标账号时，店铺和市场从账号推导；若运营另填店铺而不一致，生成前提示修正，不能自动借用其他店铺。
- 读取账号定位、默认风格参考、表达模式，同时继承现有 OPV 生产资料中的人物等基础资产。
- 目标账号为空的旧任务、普通探索任务继续原路径；不强迫所有业务账号马上配置新字段。
- 显式填写但不存在、拼写错误或关联冲突的目标，不能静默退回店铺通用池。

**A2．参考图与任务要求的优先级**

1. 指定商品参考包负责商品颜色、版型和细节；人物包负责人物身份。
2. 账号固定资料负责长期摄影基准和内容定位。
3. 本篇地点、温度条件、选题和补充要求负责当篇内容。
4. 任务参考图按既有多用途解析借鉴环境、搭配和摄影，不替换商品或人物身份。

账号参考图优先作为默认 VISUAL_STYLE；任务里的 OUTFIT／ENVIRONMENT 图不会因为数量更多就覆盖账号摄影方向。同图可多用途，但必须明确实际用途。下载和复用沿用现有附件缓存，不新增第二个素材库。

本篇可以轻微调整场景光线，不因为自然昼夜或室内外变化认定定位冲突；确实要大改账号摄影方向时修改账号配置，影响后续新任务。

**A3．冻结、队列与投递**

- `target_publish_account_id`、账号配置指纹随任务进入 release manifest 和主队列，纳入已有 hash 校验语义；新字段对无绑定的旧 manifest 可缺省。
- 对指定账号候选，排班只允许该真实账号领取；仍必须满足原有店铺、渠道能力、带货范围、时间和配额条件。
- 防止另一方向的混入：已配置本轮定位的重点账号，其原生图文槽默认只领取明确绑定自己的图文，不继续领取未绑定的公共图文池。该限制只针对原生图文，不影响其原有短视频／带货视频。
- 目标账号暂停、无能力或无可用时段时，保留待排期和具体原因，不转发给同店其他账号。
- 将匹配检查放在所有相关选片路径共用的入口，包括初始化／养号分支；实际提交前再核对 slot 账号与冻结目标，避免排班后变更或其他入口绕过。
- 内容定位变更只影响新任务，不能把已经生成、排期或发布的内容静默换账号。未提交内容如需转账号，走已有修订／重排流程；不得改写已发布记录。
- 用了商品不等于发布挂车：原生图文继续当前 CreatOK 非挂车路径，商品身份留在 source_product_id 等既有上下文，不因填写编码自动改 cart_enabled。

主要落点：图文包 `services/feishu_workflow.py`、`services/photo_request_factory.py`、`services/main_schedule_bridge.py`、`services/release_gate.py`、建表脚本；发布器 `app/scheduler.py`、`app/db.py`、`app/models.py`。

**五、工作包 B：同一旅行流程，两种表达方式**

不新增两个近似 Recipe，不改旧 legacy 一衣多穿。沿用 `PHOTO_TH_TRAVEL_OUTFIT_V2`，以可选账号表达模式控制规划文案和少量排版。未配置表达模式时保持旧输出逐字／逐结构兼容。

**B1．likeU：搭配灵感与同商品多搭配**

- 指定商品时复用已有“四套都保留商品”规则，允许其他单品、穿法和场景自然变化。
- 不沿用旧一衣多穿“所有下装鞋包都固定”的限制；可变化的范围取决于商品占用的槽位。
- 标题强调这件商品的搭配价值；每套名称或正文说清实际变化，而不是只列四个地点。
- 只有四套实际使用同一指定商品，才使用“同一件／一衣多穿”承诺。无商品时仍可做旅行灵感，但不能凭四件相似外套声称是同款。
- 不把每篇都锁定为“一衣多穿”；账号定位提供长期方向，当篇主题仍由任务选择。

**B2．第二账号：实用旅行穿搭指南**

- 每篇回答一个具体穿搭问题，例如步行、温差、穿脱、拍照搭配；不扩展成交通、门票、营业时间等完整旅游攻略。
- 标题、封面、caption 和逐页建议同题同地点。每个建议必须与画面和规划的服装相符。
- 明细页允许“造型名称＋一句具体穿搭理由”；不机械要求所有页都加长文。
- 保留当前四页旅行结构：Look A 作为首图，不额外再放一次 A。A 的详细理由可放 caption，B/C/D 使用轻量说明。
- CTA 根据本篇目的可用收藏、提问或选择，不再固定全部 A/B/C/D 投票；不生成保证效果、保证保暖或虚构旅行体验的文案。
- 不强制每篇导购。商品相关引导必须准确，橱窗对应未核实前不自动写“主页有同款”。

**B3．必须检查的完整文案链**

不能只修改 `_travel_plan_prompt`：还要检查模型响应标准化、计划冻结、`build_theme_copy`、`_display_slide_texts`／短标签裁剪、旅行四页转换、排版行数、最终页面 QA 和发布标题。

- 新表达模式产生的短理由不得被旧“只保留造型名称”函数裁掉。
- 最终页面 QA 读取当前表达模式和冻结文本，不能把新增合法第二行误判为排版错误。
- 继续使用现有 `slide_texts` 等结构；确需存每个 Look 的理由时只增加可选字段，不重建文案 schema。
- 默认账号保持旧短文案；不要为了指南模式扩大所有模板的字号／行数限制。
- 生成与文案共用当前规划调用，不增加一个独立文案模型阶段。

主要落点：`services/photo_reference_vision.py`、`services/photo_content_planner.py`、`services/photo_theme.py`、当前旅行布局渲染与最终页检查模块、`config/travel_theme_templates.json`。

**六、工作包 C：旅行流程接入账号视觉基准**

当前通用参考流程已有 color_grading_plan，旅行两步分析／规划未完整产出这一合同；部分色彩检查还以 `human_scene = scene_model and not travel_planned` 为条件。本轮补的是旅行消费账号基准，不是把全部历史 QA 开到 strict。

1. 账号视觉文字与参考图进入旅行参考分析和规划，形成一份明确的 color_grading_plan。复用现有结构，不再新建第二个“调色模板”。
2. 在旅行 normalizer、`build_travel_style_profile`、内容计划、供给请求和 image_generator 中完整保留该计划。不能模型产出了字段，标准化又丢掉。
3. 每篇及同批图片使用冻结基准；后续新任务默认继承同账号基准，任务参考图只在用途范围内补充。
4. likeU 初始建议：中性奶白底、自然肤色、柔和对比与低至中饱和，冷感作为轻微摄影倾向；奶白暖感用于兼容场景，不逐篇任意二选一。第二账号：自然日光、柔和对比、干净构图与适度留白。上述是初始可编辑建议，最终以运营已有文字／选定参考图为准。
5. 产品真实色和自然肤色优先。不得为了统一奶白色调，把黑色商品洗灰、把肤色变白或压掉细节。
6. 旅行色彩一致性默认做观察和明显异常提示；整图色彩统计会受景点与昼夜影响，不能作为账号风格的一票否决或自动付费重生理由。
7. 不新增强 LUT、精确色温阈值或独立付费色彩 QA 调用。先在已有视觉检查中补观察信息，真实样片证明仍有问题再考虑后期调色。

账号级一致性验收跨至少两篇内容，不能只看一篇四张图；自然场景色差允许保留。

主要落点：`services/photo_reference_vision.py`、`services/photo_style_reference_supply.py`、`services/image_generator.py`；复用 `services/photo_color_consistency.py`，不把 strict 设为默认。

**七、工作包 D：月份、温度与商品承诺保持一致**

这是表达模式的配套工作，不是新建天气系统。

- 当前旅行配置已有 15–22、10–15、5–10、0–5°C 等温度档；月份可以在现有内容要求中输入，但不能自动据月份编造当地实际天气。
- 账号表的“5°C旅行穿什么／10月东京怎么穿”是文案示例，不是每条任务的事实。
- 本篇地点、月份和温度要求解析后保存在现有选题快照；温度来源标明是运营给定／已有执行档位，未提供时不输出确定天气结论。
- 统一当前温度分支“只用温度档”与标题数字的口径：运营明确给了5°C，可作为该篇的穿搭假设；不让模型自由推算精确数字，也不把0–5°C档任取一点伪装成实时气温。
- 温度不再是新的必填项。缺少时可做普通目的地穿搭，不能因此卡住非温度内容。
- 不新增实时天气 API。需要讲月份气候事实时由运营提供可靠依据；不生成更大范围的旅游事实建议。
- 指定商品沿用真实款色参考包与已有核心商品 QA。已有商品／店铺／橱窗数据能查则检查对应；查不到时如实标未核实，不建设橱窗同步大工程，不自动承诺“主页同款”。

**八、已有恢复机制必须一并保护**

新增账号、表达模式和视觉基准会影响输入指纹，不能重演“加字段 → 旧计划失配 → 归档所有图片 → 再付费生成”。

- 无新配置的历史任务沿旧规则恢复，不自动补用当前账号最新定位。
- 新任务冻结目标账号和配置；重拍、续跑只消费冻结版本。
- 仅调整文案表达且视觉计划未变，可沿 `70d82bc` 的受限兼容复用源图、重新排版；不是全局删掉 hash 中的文案字段。
- 修改实际摄影风格、人物、商品或场景属于视觉变化，走已有修订流程。
- 调整投递账号不修改原已发布内容；未发布转账号也必须核对店铺、定位与已有版本边界。
- 素材登记继续使用已修的防覆盖插入和并发处理，不为了账号分组复制／改写旧素材 ID。

**九、分阶段实施和验收**

| 阶段 | 工作 | 通过标准 |
|---|---|---|
| Phase 0 | 核实两个真实账号、配置来源和当前基线；列出拟变更文件 | 不猜账号映射；不覆盖其他会话代码；旧回归可复现 |
| Phase 1 | A：账号资料同步、任务绑定、快照、队列与投递隔离 | 同店两账号不会串图文；历史公共任务和视频行为保持 |
| Phase 2 | B/C/D：两种表达、旅行视觉基准、月份温度与商品语义 | 同Recipe能体现两个定位；全链文案不被裁丢；不新增重生循环 |
| Phase 3 | 小样验证与有限上线 | 两账号各两篇，验证跨篇一致性、队列归属和恢复，按已有授权发布 |

必要自动测试：

1. 同店 A 绑定内容不能被 B 领取；A 配置为重点图文账号后不领未绑定公共图文；无新配置的旧账号仍按原逻辑运行。
2. 目标暂停、能力不足、店铺冲突时保持等待或明确错误，不能换号；同账号不同渠道共享定位且带货规则不变。
3. 排班和实际提交前都核对目标；修改队列目标而与冻结清单不符不能提交。
4. 账号配置修改不改变旧任务重拍／续跑；缺少新字段的历史任务正常恢复。
5. 指南理由从规划经过最终文案转换、四页渲染和 QA 仍可见；默认模式保留旧输出。
6. 指定商品一衣多穿保持同款身份；无商品不能输出同款承诺；商品参考同时保留摄影／环境参考。
7. 账号视觉合同经旅行 normalizer 进入四张生成请求，商品色与肤色优先，无新配置不影响既有请求。
8. 未提供月份或温度不强行猜测；提供明确条件时标题、规划和页面一致。
9. 保留素材冲突不覆盖、核心商品定向重拍、文案修复零生成等近期修复测试。

全量回归沿用图文包 unittest；因改动发布调度，补发布器相关候选筛选、排班、图文冻结与 CreatOK 测试，而不只跑 CLI 适配测试。新的期望差异必须限定于已配置的账号；不能刷新全部 TH 黄金快照来掩盖漂移。

真实样片建议共四篇：

- A账号：同一真实商品，两种旅行场景各一篇，检查搭配变化、商品一致与跨篇视觉基准。
- B账号：一个目的地拍照／步行穿搭问题、一篇运营明确温度条件的指南，检查是否实际提供建议。
- 先验队列归属；只对已有确认发布授权的记录发布，不默认发出全部四篇。
- 选择一次单Look重拍或文案修订，确认不重生其他图、不串账号、不重复入队。

不要求为每种组合全部跑付费测试。图文视觉“像账号”、文案“对题”和真实账号“收到自己的内容”分别留证。

**十、上线与交付边界**

- 先只给确认后的两个账号配置新定位。其他 TH、MX、VN 围巾默认不启用这层新行为；不得把 VN draft／disabled 状态顺带改 active。
- 保留旧一衣多穿视频入口，不改其输出形式；新的原生图文同商品多搭配复用旅行线。
- 配置和数据库更新定向执行，不全量播种覆盖其他市场。
- 回退时停止新定位任务或恢复代码／配置，不删除源图、任务、批次、历史发布记录；已排期／外部提交先核对状态，不能回退后自动再发。
- 不增加独立“人工审核通过”步骤；沿用已有执行、确认发布与修订边界。

最终交付：准确账号映射、实际字段来源与操作说明、migration（若有）、修改文件与提交、两账号快照示例、关键隔离测试、四篇样片位置、真实投递结果或尚未发布说明、TH/MX/VN兼容证据、明确未实现项。

完成标准：运营只维护一次账号定位，任务选择账号后，图文的选题、文案、摄影基准和投递目标能够一致执行；一衣多穿与实用指南都基于现有旅行能力完成；不新增大量预设、JSON人工维护或不可恢复的生成流程。

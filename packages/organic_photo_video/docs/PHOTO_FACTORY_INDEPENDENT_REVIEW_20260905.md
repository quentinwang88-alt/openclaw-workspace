# TH 图文内容工厂独立 Review

审查日期：2026-09-05。范围：初始业务要求、原生图文 MVP 开发规格、当前本地工作树、已保存的 TH 9 篇验收产物与运行记录。只读生产系统；本轮未重新查询线上状态、修改配置、生成或发布内容。本报告是对当前未提交工作树的审查，不代表已提交版本审计。

## 一、结论

现有成果是可复用的照片任务、确定性素材组合、文件导出及人工放行基础设施。通用主题策划、主题与素材的正确对应、Recipe 逐页表达尚未交付。TH 9 篇证明了批量制作与回写路径，可以作为回归夹具，不能作为内容验收通过的样例。

无需推倒 Task / Revision / Package / 飞书 / 主发布队列。需要局部纠正 Recipe 执行合同和素材装配，并先做内容样板。仅增加素材数量、模板标签或去重百分比，不足以修复内容逻辑。

## 二、初始设计到实现的偏移

1. 最初目标是低成本生产正常当地垂直内容，Recipe 明确每页的信息、变量、人物/商品一致性。原生图文与账号测试延后是用户明确授权的范围收缩。
2. 原生 MVP 文档仍保留“合格素材复用；不足时 NEEDS_ASSET 或显式补图”，并要求 8 个 Recipe 各有人工确认样例。文档明确禁止给薄外套换标题就冒充低温方案（原生 MVP 规格第 234、461 行）。
3. 无 JSON 入口的简化是合理方向，但实现进一步变成预置 profile + 文案 + 一个可匹配素材集。用户省下的内容决策没有由内部可执行内容设计补上。
4. 至少 3 个 profile、每个至少 2 份文案被做成硬性合同（domain/photo_contracts.py:116），推动开发凑组合数量。数字不同不代表内容不同，也不是原始内容质量目标。
5. 0 图片模型调用原本是“已有合格素材时”的成本验收，后来被当成所有内容都应零调用。当前自动入口仅支持 NO_PRODUCT，Planner 固定 ASSET_REUSE，不具备从所需画面出发补齐素材的完整自动路径。不能据此声明 SOFT_PRODUCT、显式补图、通用内容规划全部完成。

原设计的不足：一次铺 8 个配方、统一 5 页，在没有合格样片和资产盘点时推进范围过宽；内容验收虽写在文档中，却缺少可执行的逐页判据。不是必须逐图调用视觉模型，而是应先建立人工确认的内容样板。

## 三、按优先级列出问题

### P1：内容质量阻塞

**1. 视觉合同没有被执行。**

- 温度 Recipe 声明 base_layer / mid_layer / outer_layer 和 layering_progression=true，但素材要求仅为 look_a / look_b / look_c / look_d / alternate。
- PhotoPlanner 按素材顺序绑定页面，既不验证分层关系，也不执行 same_identity、distinct_looks 等视觉规则。
- 证据：config/recipes/PHOTO_TH_TEMPERATURE_DRESSING_V1.json:25、119、134；services/photo_planner.py:86、113；domain/contracts.py:714 只要求 visual_rules 是字典。
- 后果：给换裤子的图片配上“加一层”文案仍能通过。

**2. 自报标签被当成内容证据。**

- TH_WOMENSWEAR_LAYERED 同时声明多城市、5/10/15°C、多场景和多个身高，没有对应的单图内容证明。
- AssetSetService 主要用集合包含判断；单图仅有下装标签。
- Travel 只将 temperature_c/style 用于匹配，目的地/场景/身高/季节虽然冻结，却没有影响画面选择或具体解释。
- 证据：config/asset_sets/ASSET_TH_WOMENSWEAR_LAYERED_V1.json:9；services/asset_set_service.py:74、112、123；Travel Recipe:162。
- 纠正：不能简单让所有变量都变成图片背景标签。城市可以是文案背景，但所承诺的活动适配、叠穿方法等必须在画面或具体说明中成立。

**3. 渲染器静默丢图，并记录了未真正绘制的来源。**

- Travel / Temperature 的封面声明 source_slots=[2,3,4]，版式却为 FULL_BLEED。
- Planner 把 FULL_BLEED 映射为 single；_compose 只绘制 source_paths[0]，不检查长度。
- 输出 lineage 仍记录全部 source_assets，不能仅用来源清单判断实际画面使用了哪些图片。
- 独立复现：输入红、绿、蓝三张图到 single，成功返回纯红结果。
- 证据：services/photo_package.py:84、92、247、263、276；services/photo_planner.py:105。

**4. 内容多样性只保证 profile / 文案变化。**

- Factory 排序先看 profile 使用数，再看素材集使用数；只有一个集时会继续复用，不报告独立内容库存不足。
- 计数仅在单次 build_batch 内，没有跨 Recipe 批次的底图使用约束。
- 独立核对 45 个 JPEG 只有 26 个不同文件哈希；加字后的文件哈希变化也不能证明底图变化。温度/旅行六篇重复相同底图序列。
- 证据：services/photo_request_factory.py:56、108；tests/test_photo_request_factory.py:65 仅断言三个 profile 不同。
- 正确去重应关注来源内容、造型差异及本篇功能；封面或总结复用详情图属于合理依赖，不应被简单比例规则误杀。

### P2：降低可维护性与交付可信度

**5. 模板配置与真实画面不一致。** normalize_photo_template 没有传递 safe_area、page_variants/regions 和透明度等内容，实际走简化满幅构图与固定顶端文字。配置有矩形区域不等于渲染使用了区域。独立验证 safe_area、page_variants 在标准化后消失（services/photo_package.py:26）。建议只实现本期需要的少量布局参数，不支持的非空配置应显式报错或迁移去除。

**6. 每篇页数与源素材数量被混用。** Planner 要求五个源角色并同时创建五个 shot，而 Choice 的封面本来是派生图；这产生无实际必要的 cover_seed/alternate，并容易出现偏移绑定。保留 5 页 MVP 没问题，但应显式定义每页引用哪些源角色，允许 3/4 张合格源图支撑 5 个信息页（services/photo_planner.py:86、113、137）。

**7. 配置版本约束弱于文档承诺。** upsert_asset_set、upsert_content_recipe 会原地覆盖同 ID 内容；当前 Recipe ID 后缀 V1 与 recipe_version=2 并存。冻结快照保护已经创建的批次，但裸版本 ID 不再能唯一解释配置内容。建议针对已发布/被引用版本限制内容覆盖，新增版本保留快照；不需要重建版本平台（repositories/rds_repository.py:165、308、1501）。

**8. 操作入口简化了，但内容审阅仍然吃力。** 15 个附件、内部 profile 名和“泰语待母语复核”，没有直接告诉运营本篇主张和各页理由。应由系统输出中文主题摘要、逐页预览与待补图说明，运营只选择/审核，技术配置继续由程序管理。

## 四、现有能力应该保留什么

保留：NO_PRODUCT 任务入口；原生 JPEG 包；Recipe/素材/文案冻结；幂等任务与失败续跑；文件哈希校验；飞书预览回写；人工放行和主队列映射。真实 9 篇记录证明生成、持久化、附件回写可以联通。

不应声称已验证：语义正确、自然泰语、每个 Recipe 可用于日常发布、缺图补齐闭环、这批内容真实发布效果。保存的记录显示生成后停在图文终审，终审放行/主队列新增/发布为零；本轮没有重查线上状态。

## 五、测试和验收应如何解释

本轮独立执行包目录 unittest discovery：534 项通过。日志 /tmp/opv-independent-review-tests.log。

这些测试覆盖大量合同、类型、状态、快照、重试、哈希和技术终审。不能将数字换算成业务完成度。Preflight 的 ready 表示配置/标签/文件可匹配，字体检查也只量文字，不代表语言或主题审核。

PhotoPackageReview / release gate 主要检查文件、选图与审核绑定。飞书人工通过写入 operator_preview=True，本身不包含逐页语义证据。人工审核是合理 MVP 设计，失效之处是没有在放量前完成一次合格样板验收，且汇报把技术检查称为正式内容验收。

还需加入能暴露当前错误的回归：single+多源拒绝；不同裤子不能满足 layering；同源同内容批量只能换字时报告库存不足；未实现布局字段拒绝；同角色来源映射可核验；生产数据库字段长度与真实 Recipe 兼容。

## 六、下一步最短路径

### 第一步：收束失败产物与能力声明

建议将三条批次标记为“技术样本，内容验收未通过”，保留证据。新任务停止使用温度/旅行当前不合格组合，已冻结批次需要单独禁止放行；停用活配置不会撤销其快照。当前 review 仅提出建议，未修改线上状态。

### 第二步：先定一篇 TH 内容样板

建议从 Pick Your Look 开始，选题为“同一件灰色短外套，配短裤还是百褶裙？”现有 B/C 图有明确下装差异，可先审核能否支持二选一。该变化需要新建小版本并复用双图对比布局，不能原地把当前四选一改名。

如业务仍坚持四选一，先准备四套有清晰比较依据的 Look，只交付一篇。不要用三个 profile 对同一组图换标题制造三篇。

生成前展示一张简单内容卡：给谁看、解决什么问题、比较什么、每页新增什么信息、拟用素材、缺少什么。内容卡保存在现有 Recipe/spec/任务计划内，不另建主题中台或要求运营填 JSON。

### 第三步：定向修复并生成一篇样片

- 修复 single 丢图、源角色/页引用映射、必要布局参数。
- 把本篇最关键的素材关系变成合同，例如同一外套、两个不同下装；真实适配由一次素材审核确认，程序保证后续不换错。
- 主题先行，素材符合则复用；缺素材明确列缺口，按预算走现有图片能力补图或人工导入。补图路线需要单独完成原生任务的连接，不能把“能力存在”当作已接通。
- 先验收完整一篇，再做三篇不同内容。文件正常、主题成立、泰语自然分别记录，不互相替代。

### 第四步：逐步恢复 Travel / Temperature

- Travel 示例：“首尔旅行，室内咖啡店与户外步行如何调整穿搭？”每页要说明活动或穿脱差异。城市可以是背景条件，不强制生成地标，也不能仅换地名。
- Temperature 示例：“一次讲清一个温度条件下的穿搭层次”。可用完整 Look + 对应部位裁切/说明卡，未展示的内层不从图片猜测；配套依据不足就补图。无需为 5/10/15°C 各复制同一帖子。
- 连续三篇完成内容审核后再测试批量。发布通道和账号测试继续按用户既定范围处理，不夹带扩展。

交付标准改为：每篇说得清主题；每页增加有效信息或明确承担封面/总结功能；文案与画面一致；有合格素材依据；运营无需写 JSON；技术重试可靠。以上满足后再提高数量。
